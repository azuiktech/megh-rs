## 2026-10-18
- Removed the unused `Occurrence` and `Enrollment` types and tables of the first draft (migration 0013 drops `occurrences` and `enrollments`) and the waitlist target `occurrence`: a class or a talk is a service, a schedule and a room with a capacity, and a waitlist entry waits for a service in a window (PR #124, issue #123)
- The nine scenarios of the design, end to end over REST (`tests/booking_scenarios_test.rs`): hair colour with the stylist free while it dries, a dentist and a hygienist taking turns, a gym floor, a talk with a waitlist, restaurant tables with a waiter on demand, a recurring class paid with a pass, a groomed pet whose owner pays, a couples massage, a float pod; each is built and run only through the REST API (PR #122, issue #121)
- Payment rules: a payment method's `eligible` AIP-160 filter must hold for every service booked (evaluated over the service's `display_name`, `mode` and `attributes`) before an appointment is paid, else `NotEligible` and nothing is booked or debited; a prepaid method's validity window is judged on the time of the appointment, not the day of booking (`Expired` outside it), so a pass valid in November can book a November class in October; both are `FAILED_PRECONDITION` over REST (PR #120, issue #119)
- A client's own calendar: when a party names a client, the times that client already has (live appointments, and holds that have not expired) are left out of the availability search, and `hold` refuses a slot that overlaps them with `ClientBusy`; a cancelled appointment or an expired hold frees the time; `BookedLine` records `during` (PR #118, issue #117)
- `order_by` on every REST list (AIP-132): comma separated fields with an optional `asc` or `desc` (`capacity desc, display_name`, `start_time desc`), applied before the page is cut; numbers compare as numbers and RFC 3339 strings as times; an unknown field or a bad list is `INVALID_ARGUMENT` (PR #116, issue #115)
- REST for the waitlist: `/api/v1/orgs/{org_id}/waitlistEntries` (a client waits for an occurrence or for a service in a window of local time) with Get, List in request order, Create (join) and soft Delete (leave); the same client cannot wait for the same target twice; the generic CRUD gets an `ORDER` per collection; migration 0012 adds `waitlist_entries.org_id` (PR #114, issue #113)
- REST for groupings: `/api/v1/orgs/{org_id}/groupings` (`kind` of `org`, `bookable`, `service` or `client`, `member_id`, `group_id`) with Get, List, Create and soft Delete; an edge is refused when it would close a loop, repeats an existing edge, or names an entity the org does not cover; the member must be covered by the org of the path, so a location joins a brand from its own path; migration 0011 adds `groupings.org_id`; a unique violation is `ALREADY_EXISTS` in every route (PR #112, issue #111)
- REST for payment methods: `/api/v1/orgs/{org_id}/paymentMethods` (passes, vouchers, coupons, insurance, cash, card: `display_name`, `owner_id`, `eligible` as an AIP-160 filter, `settlement` as `"on_spot"` or a prepaid balance of uses or money with a validity window in local time, `attributes`) with Get, List, Create, Update and soft Delete on the generic CRUD; a booking's debit shows in the balance; the `eligible` filter is stored but not yet enforced (PR #110, issue #109)
- REST for services: `/api/v1/orgs/{org_id}/services` (`display_name`, `mode`, `price` as `google.type.Money`, `steps` with their needs written as AIP-160 filters over the bookables' tags and `engaged`, `free` or `on_demand`, `variants` that add to or set the duration or price when a filter holds, `attributes`) with Get, List, Create, Update and soft Delete on the generic CRUD; a service without steps is a menu node (PR #108, issue #107)
- REST for clients: `/api/v1/orgs/{org_id}/clients` (people, pets and others who are served: `display_name`, `attributes`, `org_id`) with Get, List, Create, Update and soft Delete on the generic CRUD (PR #106, issue #105)
- REST for bookables: `/api/v1/orgs/{org_id}/bookables` (providers and rooms: `display_name`, `capacity`, `attributes`, `org_id`) with Get, List (`filter` over the fields and the tags, for example `attributes.experience_years >= 10`), Create, Update (`update_mask`) and soft Delete, on a generic `http/crud` that clients, services and payment methods reuse; until now bookables could only be created from Rust (PR #104, issue #103)
- REST paths use the plural `orgs` (AIP-122): `/api/v1/orgs/{org_id}/...`, resource names `orgs/{org_id}/...`, and the first grant of every route is `orgs:read:{org_id}` (it was `org`) (PR #102, issue #101)
- REST for appointments: `/api/v1/org/{org_id}/appointments` as one resource with `state` `held`, `booked` or `cancelled`. `POST` books in one call from a slot of `availability:search` (with a `request_id`, so a retry returns the same appointment) or holds it until `expire_time`; the posted slot is only a claim: the server searches again and holds the slot it finds, so a crafted slot is refused. `POST .../appointments/{id}:confirm` turns a held appointment into a booked one under the same id, with payer, clients, payments (prepaid methods are debited) and attributes. `GET` one or a list (AIP-160 `filter` on `state`, `start_time`, `end_time`, `payer_id`, `client_ids`, `service_ids`, `bookable_ids`; an org lists the appointments of the orgs grouped under it; `show_deleted`), and `DELETE` cancels (soft: the resource returns with `delete_time`) or releases a hold. Grants: `appointments:create`, `appointments:confirm:{id}`, `appointments:read`, `appointments:delete:{id}` (PR #100, issue #99)
- REST `POST /api/v1/org/{org_id}/availability:search` (an AIP-136 custom method): parties with services (and `wants`, AIP-160 filters), a window in the org's local time (or with an offset), `party_offset`, `service_gap` and `slot_interval` as AIP-142 durations; answers the slots with their parties, allocations and price (`google.type.Money`) in local time, and `next_available_day` when nothing is open; the grants are `org:read:{org_id}` and `availability:search` (PR #98, issue #97)
- REST for schedules and blockouts: `booking_router(pool)` serves `/api/v1/org/{org_id}/schedules` and `.../blockouts` (times open for work, and closed times with a reason and notes) in the manner of the Google AIPs: Get, List (`filter` as an AIP-160 expression, `page_size`, `page_token`, `show_deleted`), Create, Update (`update_mask`) and Delete (soft: the resource comes back with `delete_time`); the hours are a `recurrence` with `TZID` and a `span`, or `days` or `date` with `start_time` and `end_time` read in the org's time zone; times in responses are in the org's zone; errors are `{"error": {"code", "message", "status"}}`; an org sees its own and its grouped orgs' rows; writes are CSRF-protected, and the paths give `authorizer` the grants `org:read:{org_id}` and `schedules:create` or the like (PR #96, issue #95)
- AIP-160 filter predicate: `Filter` is a `Predicate` that stores a Google AIP-160 filter expression such as `role = "stylist" AND experience_years >= 10` and evaluates it against an entity's key/value attributes (`AND`, `OR` binding tighter, `NOT` and `-`, implicit `AND`, `=` `!=` `<` `<=` `>` `>=` on strings, numbers, booleans and timestamps, `*` wildcards, `.` traversal, `:` has on arrays, objects and scalars; a missing field fails every restriction); parsed with the `aip-filtering` crate, whose mis-reads (a comparator without spaces, a missing right side, decimals, functions) are refused as `Invalid`; stored as `{"Filter": "..."}` (PR #94, issue #93)
- Waitlist: `Queue` implements `Waitlist`: `join` adds a client to the queue of an occurrence or of a service window, `waiting` lists the entries of a target in the order they were requested (PR #92, issue #91)
- Appointments: `Reservations` implements `Appointments`. `hold` blocks the time of a slot for a while and keeps its placements (refused with `NotOpen` outside open time and `Occupied` without capacity; holds that expired block nothing); `confirm` turns a hold into an appointment under the same id with one line per party service (client, time, price), in the org and its time zone, retry-safe with an idempotency key (the same key with another request is `KeyReused`), debiting prepaid payment methods (`Insufficient` when the balance, validity or currency does not allow it); `cancel` soft-deletes the appointment, which releases its time through the `ON DELETE CASCADE` key. Migration 0010 adds `holds.placements` (PR #90, issue #89)
- Availability search: `Slots` implements `Search`. A search is a list of parties (a client with ordered services), a window, and two controls that default to 0 (the exact same time): `party_offset`, the largest difference between the parties' start times, and `service_gap`, the largest gap between one party's consecutive services, both tried every `slot_interval`. A slot lists the allocations (provider and room, `engaged`, `free` or `on demand`), the placement of each party's service and the price; a variant changes duration and price for the matching provider or client, `wants` filter the bookables, existing appointments, unexpired holds and capacity (capacity 2 is double booking) are respected, and `org` limits the search to an org and the orgs grouped under it. `Search::next_day` gives the first local day with a slot after the window. Combinations with `itertools`, the org time zone with `chrono-tz` (PR #88, issue #87)
- Schedules, blockouts and availability: `Calendar` implements `Availability::open`, the open time of a (org, service, bookable) combination: the schedules of the nearest level that defines any (inner to outer through the grouping graph, longest path for several parents) minus every matching blockout; recurrence with the `rrule` crate (`DTSTART;TZID=...` keeps local hours across daylight saving), interval sets with `rangemap`, the grouping graph and its cycle check with `petgraph` (PR #86, issue #85)
- Service templates: `Service` implements `Templates` with `simple` (one provider and one room), `with_cleanup` (a room-only step after the client leaves), `processed` (prep, wait with the provider free, finish), `handoff` (providers taking turns), `room_only` and `session` (a class with a capacity); each returns an ordinary service of ordinary steps (PR #84, issue #83)
- Booking core types and schema: `megh::booking` row and value types (bookable, client, service with steps, needs and variants, schedule and blockout, occurrence, enrollment, hold, appointment, occupancy, payment method, waitlist entry, search request with parties and offsets), the trait signatures `Availability`, `Search`, `Appointments`, `Waitlist` and `Templates`, and migration 0009 (12 tables with the entity stamps, `ON DELETE CASCADE` keys for the soft-delete cascade); no behaviour yet (PR #82, issue #81)
- Design document for a generic booking module (`docs/TPD-booking.md`): services made of steps, bookables, schedules and blockouts, availability search, appointments, payments; research of NexHealth and Mindbody, every decision, and the PR plan (PR #80, issue #79, parent issue #78)

## 2026-10-13
- `GET /auth/{p}/connect` (session required, repeated `scope`) adds another account of the signed-in user, `POST /auth/{p}/disconnect` revokes it at the provider (best effort) and marks it disconnected, `POST /auth/{p}/revoke` revokes a token; every route needs a session and the account's email must be the user's; login and connect use `state` and PKCE kept in the session, and the sign-in popup escapes the JSON it embeds (PR #76, issue #40)

## 2026-10-05
- Fix: the UI SDK drops its cached CSRF token when signing out, so the sign-in after a sign-out no longer fails once with 403; vitest added to the SDK (PR #75, issue #74)
- Fix: `megh::migrate` now runs migration 0008 (soft delete), which was missing from its list so `deleted_at` was never added and sign-in failed with "no column found for name: deleted_at`; it can also run again on a migrated database (0001 no longer recreates the renamed `org` tables, 0002 no longer indexes the dropped `users.subject`), as applications call it on every start (PR #73, issue #72)
- Soft delete for every entity: `Entity.deleted_at` and `TableEntity::soft_delete`, which marks the row and, in one transaction, everything a physical delete would remove through foreign keys declared `ON DELETE CASCADE` (read from the catalog, repeated to the leaves of a self-referencing tree; keys without `ON DELETE CASCADE` are not followed; a dependant table without `deleted_at` and `updated_at` fails the delete and changes nothing); `update` and `upsert` refuse deleted rows; `NOT_DELETED` is the condition reads add; migration 0008 adds `deleted_at` to the tables megh maps with `Table`; `update` and `upsert` now write `SET (cols) = ROW(values)`, which Postgres accepts for a single data column (PR #71, issue #70)
- Grants per resource level: `authorizer` now requires a grant for every resource level of the request path, from `request_grants(method, matched_template, uri_path)` (one grant per level in `resource:action:instance` form; the last level takes the HTTP action or a trailing `:verb` such as `/organizations/acme:activate` or `/organizations:batchCreate`, every ancestor needs `read`; a level without an id needs `*` or no instance; no level and no action implies another; prefixes such as `v1` produce no grant; under `Router::nest` the path comes from `OriginalUri`). This also fixes routes with a leading path parameter, which were always 403 because the resource was taken from the wrong segment. `Grant` is unchanged and `request_grant` stays for callers that want one grant (PR #68, issue #67; supersedes #66, issue #65)

## 2026-09-22
- Basic login route: `basic_login_router(state, path)` (opt-in, merge with `auth_router`), CSRF-protected; `Authorization: Basic` verified against `UserRepo::verify_password`, a uniform 401 `{"error":"invalid credentials"}` for a missing header or any wrong-credential reason, never creates an account; on success returns the user and their memberships and starts a session like the OAuth callback (PR #60, issue #30)
- Redacted secrets: `OAuthProviderConfig`, `ConnectedAccount` and `OAuth2Tokens` now hand-write `Debug` to print `"[redacted]"` for `client_secret`/`access_token`/`refresh_token` instead of deriving it, and no longer derive `Serialize`, so a stray `{:?}` or `Json(..)` of one fails to compile instead of leaking the secret at runtime (PR #59, issue #58)
- OAuth token encryption at rest: `Encryptor` (AES-256-GCM, `aes-gcm`), optional and off by default; `ConnectedAccountRepo::with_encryptor`, `Accounts::with_encryptor` and `MeghAuthState::with_token_encryptor` (the same key must be given to whichever of the three an app uses, since they read and write the same columns); a decrypt failure is a hard error, never silently swallowed or treated as already-plaintext (PR #57, issue #56)
- CSRF on every write path: `events_router`'s `POST /sub` is now behind `tower-http`'s stateless Origin/Sec-Fetch-Site check by default (`events_router_with_csrf` for a trusted cross-origin app); `megh::auth` re-exports `CsrfMiddleware`/`get_or_create_token`/`TOKEN_HEADER`/`TOKEN_KEY` so an app can protect its own session-backed routes with one `.layer(...)`; the UI SDK now fetches and sends the `x-csrf-token` header on every write (`signOut` was silently broken since F16) and re-fetches it after a 403 (PR #55, issue #54)
- OAuth callback hardening: the login sends a random `state` and an S256 PKCE challenge and keeps them in the session; the callback verifies `state` (constant time, one attempt per login, consumed even when wrong), sends the PKCE verifier, and rejects an email the provider has not verified; the result page posts to a configurable `web_origin` instead of `*` with its data in escaped HTML attributes; provider, database and session failures return fixed messages and are logged, and a failed `connected_accounts` save is an error; `oauth2` gets its `timing-resistant-secret-traits` feature; `MeghAuthState::with_web_origin`; the session cookie must be `SameSite=Lax` (PR #53, issue #22)
- Audit triggers: migration 0007 adds `audit_entries` (megh-go's schema) and the functions behind `megh::audit` (`AuditTrigger::on` / `dedicated` with overridable audit table, trigger name and key column, `Audit::install`, `history` and the transaction-scoped `Audit::actor`); one shared trigger function records old and new rows as JSON, every name is quoted by Postgres, and an existing trigger of the same name (for example megh-go's) is left alone (PR #52, issue #51)
- JWT access token in front of the session: `jwt_session` middleware (`JwtSession`, `AccessToken`, `JWT_COOKIE`) verifies a short-lived RFC 9068 token from the `jwt_token` cookie with `jsonwebtoken` 11 and gives its grants to `authorizer` without a database lookup; a missing or expired token is renewed from the `tower-sessions` session (the user's first membership), any other invalid token is rejected; the cookie is `HttpOnly`, `Secure` and `SameSite=Lax`, and `POST /auth/logout` clears it. Same claims as megh-go, so tokens verify in both stacks (PR #50, issue #49)
- `Subscriptions` (billing lifecycle ported from megh-go): plans (`create_plan`, `list_plans`, `plan`, `plan_by_sku`), `add_price`, `create_add_on`, `attach_plan_add_on`, and per organization `subscribe` (replaces the subscription, pads seats to the price's included seats, starts a trial and sets a one-month or one-year period), `change_seats`, `cancel(CancelWhen::Now | AtPeriodEnd)`, `attach_add_on`, `detach_add_on`, with `BillingError` (PR #48, issue #46)
- Billing entities and money: `megh::billing` row types for the megh-go billing tables (`Plan`, `PlanPrice`, `AddOn`, `PlanAddOn`, `Subscription`, `SubscriptionItem`, the status, interval and add-on type enums, `Money` accessors) and `megh::money` (`rusty-money`, `from_micros`, `to_micros`; prices stay `BIGINT` micros); `JsonText<T>` reads the JSON that megh-go keeps in text columns, NULL as empty (PR #47, issue #45)
- Password storage: `UserRepo::set_password` (bcrypt, portable with megh-go) and `verify_password`, which returns the `User` or a `PasswordError` saying why not (`UserNotFound`, `NoPassword`, `WrongPassword`, `Hash`, `Database`); megh-go's empty `password_hash` counts as no password, and a missing user or password still costs one bcrypt verification (PR #44, issue #29)

## 2026-09-21
- Sessions and CSRF on libraries: `auth_router` uses `tower-sessions` (mount it under a `SessionManagerLayer`; the Postgres store creates `tower_sessions.session`) and `axum-tower-sessions-csrf`; `GET /auth/csrf-token` issues a token that every POST, PUT, PATCH and DELETE must send as `x-csrf-token` (403 otherwise). Removed `SessionRepo`, the `session` module, `extract_cookie`, `with_cookie_name`, `session_duration`, `with_csrf` and the `tower-http` `CsrfLayer`; `AuthUser` and `AuthMeResponse` no longer carry a session. `sqlx` back to 0.8, `tower-sessions` 0.14 and `axum-tower-sessions-csrf` =0.1.1 (see AGENTS.md); the `sessions` table from migration 0004 is no longer used (PR #43, issue #42)
- Token refresh: `Accounts` with `auth`/`auth_for` returning `AccountAuth`, a `reqwest-middleware` layer that authenticates requests as a connected account and refreshes its token when expired (row lock so concurrent requests refresh once; a rejected refresh token marks the account disconnected and fails with `AccountError::InvalidGrant`); `ConnectedAccountRepo::save` keeps the stored refresh token on re-login (PR #39, issue #36)
- `reqwest` 0.12 → 0.13: `oauth2` is used without its bundled `reqwest` adapter, and the new `oauth_http_client(client)` lets a caller-configured `reqwest` 0.13 client perform token requests (PR #38, issue #37)
- Upgrade every dependency to its latest release: `oauth2` 4.4 → 5 (typestate client, `ProviderClient`; the shared HTTP client no longer follows redirects and has a 10 s timeout), `sqlx` 0.8 → 0.9 (derive-built SQL is asserted safe), `sha2` 0.10 → 0.11, `syn` 2 → 3, plus the rest of the lockfile; `cargo audit` now reports no vulnerabilities (was 5 and 1 warning, all through `oauth2 4.4` → `reqwest 0.11`). `reqwest` stays at 0.12 (required by `oauth2` 5.0.0). Add `AGENTS.md` with the always-latest rule; mark org O1 done (PR #35, issue #34)
- O1: align the org domain with megh-go: migration `0006` renames `org`/`org_members` to `organizations`/`organization_members` (or copies rows when megh-go's tables exist), aligns columns, stores `grants` as a JSON array in `text`, and creates `organization_invites`, `org_configs` and the billing tables (schema only); `OrgMember` is renamed `Member` (adds `role`, `invited_by`); `Org` gains megh-go's columns; new `Orgs::memberships` (PR #33, issue #28)
- Align `users` with megh-go: add `account_id`, `provider`, `password_hash` (text, nullable), unique `(account_id, provider)`, drop `subject` (migration `0005`, idempotent, backfills from `subject`); one user per email across providers, the first provider's identity is kept; `UserProfile`/`UpsertUserInput` use `account_id` + `provider`, `find_by_subject` becomes `find_by_account` (PR #32, issue #27)
- CSRF protection: re-export `tower-http`'s stateless `CsrfLayer` (`megh::auth::{CsrfLayer, ConfigError, ProtectionError}`) for any router, route or Tower service, and apply it by default to every `auth_router` route, configurable via `MeghAuthState::with_csrf` (PR #26, issue #25)
- Upgrade axum to 0.8 (route params now `/{x}`), reuse `axum::extract::FromRef` in place of the hand-written trait, ignore `.env.*`, replace the OAuth-hardening TPD with the feature-level `docs/TPD-authentication-authorization.md`, and add this changelog (PR #24, issue #23)
